## PD-20: Provider-notice triage is decided at the merge by rule wherever the interface answers it (coordinator, 9 Nov)
Context: Bob, 9 Nov: "Triaging used to be pretty instantaneous... how do we get it back to a lightweight process". Since 4 Nov (19d1e91) a merge leaves a provider notice for any change to the provider's own source, with no requirement id and no export changed. The merge's triage cleared only users holding no file that imports the provider; every importing user waited for a worker BOB runs (25 modules or 250 KB per share). Widely imported providers (bundler, ai-catalogue) raise notices with 100 or more importing users per bug-fix pull request, so BOB ran many worker shares, one after another, before starting jobs.
Decision: the coordinator's, 9 Nov, at Bob's ask quoted above. When a notice changed no requirement id, and its exports were read over the pull request's range (the notice records the range and the entry files read, `exports_read`), the merge clears users by rule, writing the same triage and answered rows a worker's `not affected` writes:
1. No export changed: every user is `not affected`, worker `merge: no interface change`, its evidence the pull request, "no requirement id changed" and "exports read unchanged at <base>..<head>".
2. Exports only added: the same; an added name cannot break an importer.
3. Exports removed or changed: a user whose every import of the provider names only exports that did not move, from a file the export read covered, is `not affected` (worker `merge: imported names unchanged`), its import lines the evidence. A user that imports a moved name stays owed, as does one whose import cannot be read as names (a default, namespace, `export *`, dynamic `import()` or `require()`, a statement that cannot be parsed, a file outside the export read, such as the provider's test fixture), and every importer when a class member moved, since any instance reaches a member whatever its import names (the copy's ai-accounts T53, 4 Nov).
4. A requirement id changed: as before; the imports check clears non-importers and workers judge importers.
Anything unread fails closed: exports unread (TypeScript export forms the surface does not read, interface, type, enum, namespace, declare, abstract class, count as unread), an export read that found no entry file, no export read recorded (a notice raised before this rule, or by layer land), and under rule 3 an open job branch that changes the user's paths. The merge's imports check (`merge: imports check`) stands for every case. The merge's "notice triage <key> at the merge" line names which rule cleared how many, and each user left owed is named with why. `notice triage <key>` applies the same rules to a notice raised before them, reading its exports over its merged range, records what they clear (worker `notice triage: ...`), and briefs only the rest, each with why the rule left it.
Consequences: an internal change that keeps names and requirements unchanged is trusted to the provider's own requirement tests, the user modules' gates and the walk; a user relying on unstated behaviour is caught there, not at triage. Most bug-fix merges of a widely imported provider owe no worker. Notices that change a requirement id still owe a worker for each importing user, as before. C54 builds it.

## PD-25: The direct flow: every job is based on the tranche, and a module starts once every module upstream of it is settled (Bob, 9 Nov)
Context: under the shared layer branch a layer's jobs wait for the layer before to merge. A study of the layer-level checks (the coordinator's velocity audit, 9 Nov, "Layer study") found that no test suite runs at layer level (INT-4, Bob, 5 Nov): each layer-level check either moves to job start or the land, is already done per job, or goes. The cross-module backstop is the tranche-into-main gate, which already re-runs a user's suite whose provider changed after it was gated.
Decision, in Bob's words (9 Nov): "Because modules are in a total order, perhaps holding jobs in upper layers until an earlier layer closes isn't necessary", and "All jobs of a layer should open at once up to the maximum slot cap." On velocity: no blind reruns, no new safeguards, subtraction first. So `process/config.json` may say `"merge_strategy": "direct"`. Every job is cut from the tranche and publishes onto it (`layer publish`, which still halts a run on a reschedule). Its rows go under one key per tranche, `layerflow/direct-<tranche>/`. A module is ready when it has an unmet mark, an owed reopen or an outstanding reschedule, has no open job, and every module upstream of it in the uses graph is settled (no open job, no unmet mark, no outstanding reschedule; BLOCKED counts as settled). Every ready job starts at once, up to the slot cap (`direct jobs`, and status, the sweep and `round next`). `job start` runs that module's census. `layer land <pr>` accepts a job PR into the tranche once its gate is green, every module it uses is settled, and their interface-changing lands are ancestors of its head. A change to its interface reschedules every open user and notifies the others, and the notice is triaged at once by rule (PD-20). A ready direct job PR gets its whole suite at the gate. At the tranche into main, a land counts as gated when the land's own gate run was verified green (`jobMerge`, by layerCover's judge). A round is every flawed module at once (each recorded found mark starts its job at once), and its walk is owed once every module is settled. Modules that use each other land in map order, and the later one's land reschedules the earlier ones.
Consequences: no layer branch, layer open, layer sync, layer merge, layer gate, join, companion or early start under the direct flow. The combined state is tested only at the tranche into main, and a provider's interface change reaches more users at once. The layer flow stays in the tool until the copy's open layer 14 merges; the copy then switches its config, and the layer machinery is retired after that.
