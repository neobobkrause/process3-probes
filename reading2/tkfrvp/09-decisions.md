## BD-R4: The released-store migration test covers only the last few releases (Bob, 8 Nov)

## PD-16: A round closes at its internal walk; the live walk runs only on the release after a clean internal walk; walks run in parallel within Cloudflare's limits (coordinator, 8 Nov)
Context: under BD-R1 a round ends at its walk, and the release deployment and its walk follow only a flaw-free internal walk. The tool still ran the 7 Nov round-close run (internal walk, then a dev deploy and a live walk) every round; round 1's close deployed p3dev-l12 and walked it live after its internal walk had found flaws. Bob, 8 Nov: "The live walk will take a long time and will end up being an expensive means of identifying many of the same the flaws the internal walk found. Stop the live walk now, update the process so that the live walk only runs once a round closes with no flaws found from the internal walk. And try to configure both walks to run as many walks as is reasonable to speed up the walking process. (But be careful that there aren't too many external walkers to cause the Cloudflare system to exceed limits of the account."
Decision: the round-close run is the internal walk only; its findings open the next round. A round whose internal walk is clean (known gaps deferred on Bob's word count as passing) owes the release deployment and its live walk, and nothing else owes a live walk. Walk concurrency is configuration: the internal walk defaults to the runner's CPU count; the live walk to 85% of the tightest published Cloudflare account limit its walkers use, never above it.
Consequences: C43 changes the tool. Round 1's live arm on p3dev-l12 was stopped on Bob's word and its internal walk's findings open round 2. Until C43 is pinned, BOB runs no dev deploy or live walk after a flawed internal walk. Product walker changes needed for parallel walks go to BOB as a job.

## BD-R5: The first release walks run without an AI account; AI-assisted journeys are walked only after the non-AI journeys are clean (Bob, 9 Nov)
Context: under BD-R1 and PD-16 the release deployment and its live walk follow a clean internal walk. Some of the product's journeys are AI-assisted and need an AI account connected to the deployment.

## PD-17: New process paths are rehearsed in process3 before the product uses them (coordinator, 9 Nov)
Context: round 2 stalled on a tool cycle (found, job start --reopen, layer open) that first showed in the product, at the cost of a builder, a pin move and BOB's wait. Each pin move costs the product about 35 minutes, and a defect found there costs a fix, another pin move and another wait.
Decision: a new or changed process path the product will run (a round, a layer open, a walk, a release step) is first run end to end in process3: in a fixture test of the tool's suite (C46's round-loop rehearsal is the model) and, where the path needs a real repository or real CI, in neobobkrause/process3-probes. A builder's PR that adds such a path carries its rehearsal; the coordinator's review checks for it. A path the product reaches before its rehearsal exists is a finding against the process, not the product.
Consequences: builders write a rehearsal with each process path; tool PRs grow by that test. Probes pin moves stay with Bob's own session until coordinator-started probes sessions can push. Defects in the round loop are caught before a pin move, not after.

## PD-18: A provider notice whose pull request does not exist is withdrawn by the tool (coordinator, 9 Nov)
Context: BOB found 4 provider notices in the copy (publication:632, network-notices:633, case-import:635, case-authoring:681) naming pull requests GitHub does not have (404). `notice triage` refuses to brief them and `notice withdraw` refuses any unmerged pull request, so they could never be answered or cleared and held the triage count up for good.

Consequences: C48 builds it. BOB withdraws the 4 after the next pin move, and until then triages the rest.

## PD-19: A module whose change a job in the open layer needs joins that layer as the job's companion (coordinator, 9 Nov)
Context: in the product copy, round 2 · layer 2 (internal layer 14) is open with jobs ai-catalogue, ai-accounts and credentials. ai-accounts and credentials have their code done and green in their own modules, but they declare new ops (aikeyreference, aisignin, alertconnect; ai-catalogue declares aicatalogueread and airesultsread). Declaring an op needs companion edits in another module: op-declarations (its t48 'own' family, ACT_HELP_ABSENT, the t48.test list) and, for ai-catalogue, store-assembly's routing and imports. Without them op-declarations' own suite goes red (measured: 273 pass / 3 fail with the jobs, 268 / 0 without). `layer join` joins only a later layer ("no layer follows layer 14 in build/layers.md: op-declarations has no next layer to join"), so there was no route to add a companion module to the open layer, and the jobs were blocked.
Decision: a module whose change a job in the open layer needs (a registry or assembly module such as op-declarations or store-assembly) may join that open layer as a companion job: `layer join <companion> --companion-of <job> --layer <n> --why "<what it needs>"`. It lands in the same layer as the job that needs it, and the dependent job lands only after its companion. It is never a way around the plan: the companion's change is limited to what the named job needs, and the layer's checks at close run as for any member. The join is refused when the layer is not open, the job is not in it, the companion is the job, the companion has an open job anywhere, or it is held, blocked or deferred there.
Consequences: C51 builds it: a companion row and a join row on the state branch; the companion's start and brief name the dependent job and the why; `layer land` refuses the dependent job until its companion has landed and its head holds that land; `layer status`, `layer jobs`, `round next` and status show companions; the layer merge waits for both. BOB joins op-declarations (for ai-accounts, credentials and ai-catalogue) and store-assembly (for ai-catalogue) to layer 14 after the pin move that carries C51, each before its companion's job starts.

### PD-19b: A companion no longer orders lands (coordinator, 9 Nov)
Context: Bob's audit of 9 Nov asks that safeguards added without his approval be removed. In the copy, layer 14 deadlocked on PD-19's land order: the companion op-declarations (PR 1104) declares ops that exist only in its dependents ai-accounts (1098) and credentials (1099), so its own suite is red until they land, and they could not land until it did; none of the three could land. Merged together the suite is green (282/282).
Decision: a companion does not order lands. `layer land` no longer holds a dependent job until its companion has landed; the job and its companion land in the same layer, in any order, and the layer's merge gate checks the layer whole, as it already does. The companion rows, `layer join --companion-of` and the status lines stay, as information only.
Consequences: C55 removes the land hold (companionsPending and its refusal in `layer land`), drops the dependent's "lands after its companion" listing in `layer status`, `layer jobs` and `round next`, and rewords the status lines, the join message and both briefs to say they land in the same layer. The test of the hold is removed and one test lands a dependent before its companion. No new check is added.

## PD-20: Provider-notice triage is decided at the merge by rule wherever the interface answers it (coordinator, 9 Nov)
Context: Bob, 9 Nov: "Triaging used to be pretty instantaneous... how do we get it back to a lightweight process". Since 4 Nov (19d1e91) a merge leaves a provider notice for any change to the provider's own source, with no requirement id and no export changed. The merge's triage cleared only users holding no file that imports the provider; every importing user waited for a worker BOB runs (25 modules or 250 KB per share). Widely imported providers (bundler, ai-catalogue) raise notices with 100 or more importing users per bug-fix pull request, so BOB ran many worker shares, one after another, before starting jobs.
Decision: the coordinator's, 9 Nov, at Bob's ask quoted above. When a notice changed no requirement id, and its exports were read over the pull request's range (the notice records the range and the entry files read, `exports_read`), the merge clears users by rule, writing the same triage and answered rows a worker's `not affected` writes:
1. No export changed: every user is `not affected`, worker `merge: no interface change`, its evidence the pull request, "no requirement id changed" and "exports read unchanged at <base>..<head>".
2. Exports only added: the same; an added name cannot break an importer.
3. Exports removed or changed: a user whose every import of the provider names only exports that did not move, from a file the export read covered, is `not affected` (worker `merge: imported names unchanged`), its import lines the evidence. A user that imports a moved name stays owed, as does one whose import cannot be read as names (a default, namespace, `export *`, dynamic `import()` or `require()`, a statement that cannot be parsed, a file outside the export read, such as the provider's test fixture), and every importer when a class member moved, since any instance reaches a member whatever its import names (the copy's ai-accounts T53, 4 Nov).
4. A requirement id changed: as before; the imports check clears non-importers and workers judge importers.
Anything unread fails closed: exports unread (TypeScript export forms the surface does not read, interface, type, enum, namespace, declare, abstract class, count as unread), an export read that found no entry file, no export read recorded (a notice raised before this rule, or by layer land), and under rule 3 an open job branch that changes the user's paths. The merge's imports check (`merge: imports check`) stands for every case. The merge's "notice triage <key> at the merge" line names which rule cleared how many, and each user left owed is named with why. `notice triage <key>` applies the same rules to a notice raised before them, reading its exports over its merged range, records what they clear (worker `notice triage: ...`), and briefs only the rest, each with why the rule left it.
