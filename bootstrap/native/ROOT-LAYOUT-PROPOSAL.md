# Proposed addressable ROOT role — awaiting owner decision

The standing depth0 chat has not demonstrated message-triggered idle wake. A delayed
child prepared its result about72seconds before a scheduled ROOT entry; its result
was presented after that entry. No notify_parent tool exists in the actual tested
child inventory. Documented CLIqueue has neither a current hosted-ROOT binding nor
a reachable default local daemon. None of those observations establishes universal
platform impossibility, and the timer is not reactive transport.

## Concrete alternative and measured result

Keep the current chat as an owner-facing console and safety runner. Place Process4's
ROOT role in a retained native child that can be addressed by supported followup_task.
ROOT retains its liveness/session duties, ARCH product decisions/jobs, coordinator
owner liaison, and JOB module ownership. No grant or provider permission changes.

| Function | Proposed native location |
| --- | --- |
| Owner console / safety runner | Existing chat, depth0; relays owner input and replaces ROOT role when active |
| Process4 ROOT | Retained native child, depth1 |
| ARCH and coordinator | Distinct children of ROOT, depth2 |
| Module JOBs | ARCH children, depth3 |
| Watcher | Beside ROOT at depth1, created by console; never creates its own successor |

Historical PLT-5 and permissions_inventory explicitly use zero-indexed depth≤3,
including four nodes. Earlier assessment incorrectly compressed this to three
nodes. The proposed maximum native depth3 fits that historical numeric bound;
this does not by itself settle what the owner means by the first owner-started ROOT.

A segregated read-only native fixture actually created the full depth0→1→2→3
chain, without changing operating role registrations. A JOB atdepth3 woke the idle
supervisory ancestor atdepth1 in11.139seconds. The JOB performed independent work
while the recipient withheld its final45seconds. A distinct coordinator answered
a clearly synthetic owner question without starting a build or another session.

The active console interrupted supervisory generation1 while running, created a
distinct sibling generation2, and that replacement recovered the unfinished fixture
supervision step. It contacted the retained ARCH across the old subtree without
reparenting native lineage. The retained JOB then woke idle generation2 across the
changed path in13.542seconds. These are observed model/tool timings to first shell
action, not service latency or SLA. No source/provider/credential operation occurred.

## Important limits and transition implications

- This does NOT make the existing depth0 chat reactively wake. It changes which
  session holds the Process4 ROOT role. That is the decision being requested.
- Owner input starts this console normally; it can promptly forward exact text to
  the distinct coordinator and return its answer while active. The console must
  not turn questions into build instructions or make product decisions.
- Proactive owner-visible notifications while the console is idle remain limited.
  They may wait for console continuation. Internal role messaging can be reactive.
- Replacement was demonstrated with the console active. If ROOT is unavailable
  while the console is idle, its safety timer must start the console before it can
  create the sibling replacement. No instant failover or deleted-chat resurrection
  is claimed. A watcher must not spawn ROOT under itself and grow JOB depth to4.
- One extra retained native session/context adds subscription-allowance overhead;
  no hosting purchase, metered inference or new account authorization is proposed.
  Available native concurrency can be lower than the owner's account job-slot cap;
  the implementation must narrow dispatch without changing that cap.
- Typed controller and existing provider protections remain in force. Inherited
  alternative tools still exist; this is not physical credential/tool isolation.
- Current production controller role registrations have NOT been remapped. On
  approval, add explicit layout selection and ROOT binding, generation-safe routing,
  console/coordinator forwarding and automatic safety recovery, then verify a native
  development cycle under that mode. Keep the current mode and branches preserved.

## Recommendation

Adopt this native addressable ROOT-role arrangement for the experimental bootstrap,
with the console/safety and owner-notification limits above stated explicitly. It
uses demonstrated supported mechanisms and preserves functional role authority,
without paid infrastructure or GitHub as a message bus.

Approval is needed for the ROOT identity/requirement interpretation: the owner's
latest guidance specifically identifies the idle top-level ROOT as the unresolved
problem. We must not silently declare a different child to be that same session.
This is not a request to broaden grants, weaken consequential prohibitions, add
product-test stages or require another login. If the depth0 chat itself must remain
ROOT and wake immediately, the available supported surface still lacks that proof.
